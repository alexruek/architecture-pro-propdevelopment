# Требования к внешним интеграциям. Умный домофон и умный шлагбаум

## Контекст

PropDevelopment внедряет два новых сервиса «Умного дома» через партнёрские платформы:

* **Умный домофон** — видеодомофон с биометрическим распознаванием лиц
* **Умный шлагбаум** — управление шлагбаумом с распознаванием государственных номеров ТС

Оба сервиса доступны собственникам через существующее мобильное приложение.
Все вызовы к партнёрам проходят через новый компонент **`smart-home-gateway`**.

## 2. Протоколы аутентификации и авторизации

### 2.1 Аутентификация собственника (мобильное приложение → шлюз)


| Аспект                  | Решение                                                                                                                                             |
| ----------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Протокол              | **OAuth 2.0 + OpenID Connect**                                                                                                                             |
| Сервис                  | Существующий`auth-service-1`(Keycloak)                                                                                                         |
| Тип токена           | **JWT (Bearer token)**с коротким TTL (15 мин) + Refresh token                                                                                  |
| Claims в JWT                 | `sub`(ID собственника),`apartment_id`,`building_id`,`roles`                                                                                    |
| Хранение токена | Только в защищённом хранилище мобильного устройства (Keychain/KeyStore)                                      |
| MFA                           | Рекомендуется для операций управления списком доступа (добавление/удаление лиц, ТС) |

### 2.2 Авторизация запросов на шлюзе


| Аспект     | Решение                                                                                                                                                                                                      |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Механизм | **RBAC**на основе claims из JWT                                                                                                                                                                           |
| Роли         | `owner`— полный доступ к своему устройству;`guest`— только открытие;`admin`— управление всеми устройствами жилого комплекса |
| Проверка | Шлюз валидирует: (1) подпись JWT, (2) TTL токена, (3) соответствие`building_id`в токене и запрашиваемом устройстве                            |

### 2.3 Аутентификация шлюза у партнёра (machine-to-machine)


| Аспект               | Решение                                                                                                                                                                                                      |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Протокол           | **OAuth 2.0 Client Credentials Flow**                                                                                                                                                                               |
| Идентификация | `client_id`+`client_secret`для каждой партнёрской системы отдельно                                                                                                               |
| Токены               | Партнёрские access tokens кэшируются на шлюзе до истечения TTL                                                                                                               |
| Ротация             | API ключи и секреты ротируются не реже 1 раза в 90 дней                                                                                                                       |
| Принцип             | Credentials PropDevelopment**никогда**не передаются в мобильное приложение; credentials пользователя**никогда**не передаются партнёру |

### 2.4 Схема потока авторизации

```
Собственник
  │
  │  [1] Логин → JWT (OAuth2/OIDC)
  ▼
Мобильное приложение
  │
  │  [2] REST + Bearer JWT
  ▼
smart-home-gateway
  │  [3] Валидация JWT (подпись, TTL, claims)
  │  [4] Проверка прав на конкретное устройство
  │  [5] Получение/обновление партнёрского access token (Client Credentials)
  │
  │  [6] HTTPS + OAuth2 Bearer (партнёрский токен)
  ▼
Партнёрская система (домофон / шлагбаум)
```

## 3. Организация взаимодействия между системами

### 3.1 Архитектурное решение

Все вызовы к партнёрским системам проходят **исключительно через `smart-home-gateway`**.
Шлюз является единственной точкой, которая:

* знает credentials партнёров,
* авторизует запросы собственников,
* логирует все операции,
* применяет политики безопасности.

### 3.2 Взаимодействие компонентов


| Направление                                         | Протокол                          | Аутентификация      | Формат |
| -------------------------------------------------------------- | ----------------------------------------- | --------------------------------- | ------------ |
| Мобильное приложение →`smart-home-gateway` | HTTPS/REST                                | JWT Bearer (OAuth2)               | JSON         |
| `tenant-core-app`→`smart-home-gateway`                        | HTTP/REST (внутренняя сеть) | mTLS или service account token | JSON         |
| `smart-home-gateway`→ Система домофона         | HTTPS/REST                                | OAuth2 Client Credentials         | JSON         |
| `smart-home-gateway`→ Система шлагбаума       | HTTPS/REST                                | OAuth2 Client Credentials         | JSON         |

### 3.3 Синхронизация прав доступа

```
tenant-core-app
  │
  │  При изменении данных собственника (въезд/выезд, добавление гостя):
  │  POST /smart-home/access-rules  [REST]
  ▼
smart-home-gateway
  │
  │  Трансляция в формат партнёра:
  ├──► Система домофона: PUT /residents/{building_id}/faces
  └──► Система шлагбаума: PUT /residents/{building_id}/plates
```

### 3.4 Обработка сбоев партнёрских API


| Сценарий                                                  | Поведение                                                                                                                                                                                             |
| ----------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Партнёрский API недоступен                   | Шлюз возвращает HTTP 503 с понятным сообщением; мобильное приложение показывает пользователю статус недоступности |
| Таймаут (> 5 сек)                                       | Circuit breaker разрывает соединение; повторная попытка через 30 сек                                                                                                |
| Ошибка авторизации у партнёра (401/403) | Шлюз логирует инцидент, уведомляет дежурного инженера, возвращает 503 пользователю                                                        |
| Недоступность шлюза                             | Резервный экземпляр (`hot standby`) поднимается автоматически                                                                                                        |

### 3.5 Контракт API с партнёром

Перед подключением каждой партнёрской системы необходимо:

1. **Провести анализ API контракта** на наличие избыточных данных (см. текущую проблему компании — SEC-15)
2. **Зафиксировать в контракте:**
   * Перечень передаваемых категорий данных
   * Запрет на использование данных PropDevelopment в собственных целях партнёра
   * Право на аудит партнёра
   * Сроки хранения и условия удаления данных
3. **Подписать DPA** (Data Processing Agreement) в соответствии с требованиями ФЗ-152

### 3.6 Мониторинг и SLA


| Метрика                                      | Порог                                             | Действие                                            |
| --------------------------------------------------- | ------------------------------------------------------ | ----------------------------------------------------------- |
| Доступность шлюза                   | ≥ 99.5%                                               | Алерт дежурному инженеру              |
| Доступность партнёрского API | < 99% за сутки                                  | Уведомление партнёра, эскалация |
| Латентность p99                          | > 3 сек                                             | Алерт, анализ bottleneck                         |
| Число ошибок авторизации      | > 10 за 5 мин                                     | Алерт (возможная атака)                  |
| Неудачные попытки открытия  | > 5 за 1 мин с одного устройства | Временная блокировка, алерт         |
