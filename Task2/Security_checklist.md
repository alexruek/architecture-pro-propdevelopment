# Проверочный лист безопасности бизнес-систем PropDevelopment

## 1. Обоснование выбора разделов

Выбор разделов проверочного листа основан на анализе архитектуры PropDevelopment, выявленных проблем и требований бизнеса. Каждый раздел обоснован конкретными рисками.


| № | Раздел                                                              | Обоснование выбора                                                                                                                                                                                                                                                                               |
| -- | ------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1  | **Управление доступом (IAM)**                           | Несколько несвязанных точек регистрации клиентов; клиенты видят данные других пользователей в ЛК — прямое свидетельство проблем с изоляцией сессий или авторизацией |
| 2  | **Защита персональных данных (ПДн)**           | Компания обрабатывает ФИО, телефоны, e-mail, биометрию (онлайн-тур), финансовые и юридические данные (онлайн-сделка). Требования 152-ФЗ и 187-ФЗ обязательны                                   |
| 3  | **Безопасность внешних API и интеграций**   | Партнеры (управляющие компании) могут видеть и изменять данные клиентов других УК. Нет единых политик безопасности при интеграции с платежной системой и СМЭВ                |
| 4  | **Разграничение доступа к данным**             | Хранилище данных (Greenplum, S3) не имеет ограничений доступа. Это блокирует развитие BI/ML-направления и создает риск массовой утечки                                                                           |
| 5  | **Аудит и логирование событий**                   | Специалист по ИБ не получает информацию о всех изменениях из-за смены руководства. Нет системного контроля внутренних потоков данных                                                             |
| 6  | **Сетевая безопасность и сегментация**     | Гибридная инфраструктура (on-premise + облако). Firewall только на внешнем периметре. Внутренняя сегментация не описана                                                                                                        |
| 7  | **Управление секретами и конфигурацией** | Множество БД (MSSQL, PostgreSQL, Greenplum, S3) с разными технологиями — высокий риск неконтролируемого хранения credentials                                                                                                                  |

---

## 2. Методология

- **Стандарты:** ISO/IEC 27001:2022, ISO/IEC 27002:2022, OWASP ASVS v4
- **Законодательство:** 152-ФЗ «О персональных данных», приказы ФСТЭК
- **Горизонт оценки:** текущее состояние архитектуры до проведения аудита
- **Источники данных:** описание системы, диаграмма контейнеров C4
- **Статусы:** ✅ Выполнено | ⚠️ Частично | ❌ Не выполнено | ❓ Нет данных

## 5. Топ-5 критических уязвимостей (вывод)

1. Нарушение изоляции данных клиентов - клиенты видят чужой ЛК. Вероятная причина: отсутствие проверки tenant ownership при получении данных из `client-crm-app`.
2. Отсутствие tenant isolation в API партнёров ЖКУ - партнёр одной УК может читать и изменять данные другой УК. Требует немедленного введения API Gateway с проверкой контекста.
3. Хранилище данных без ограничений доступа - весь корпоративный датасет (ПДн клиентов, финансы, сделки) доступен без RLS. Блокирует развитие BI/ML и создаёт риск массовой утечки.
4. Отсутствие централизованного аудита событий безопасности - специалист ИБ работает вслепую. При инциденте невозможно провести forensics-анализ.
5. Передача ПДн в DWH без обезличивания - данные копируются через CDC напрямую из операционных БД, нарушая требования 152-ФЗ о минимизации обработки данных.
