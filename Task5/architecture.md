# Архитектурное решение

## Контекст

PropDevelopment имеет два изолированных контура сервисов в рамках одного кластера:


| Контур                     | Frontend          | Backend API          | Назначение                                          |
| -------------------------------- | ----------------- | -------------------- | ------------------------------------------------------------- |
| Клиентский             | `front-end`       | `back-end-api`       | Витрина продаж, client-mart-app, client-tour-app |
| Административный | `admin-front-end` | `admin-back-end-api` | client-crm-app, управление данными           |

Смешивание трафика между контурами недопустимо: менеджер CRM не должен иметь доступ через клиентские API, а клиент — к административным сервисам.

## Принятые архитектурные решения

### 1. Default Deny All как базовая политика

Политика `default-deny-all` с пустым `podSelector: {}` блокирует **весь** входящий и исходящий трафик для всех подов в namespace. Это принцип Least Privilege на сетевом уровне — явное разрешение лучше неявного запрета.

### 2. Явное управление Ingress и Egress

Для каждого разрешенного потока созданы **отдельные политики** для обоих направлений:

- Egress на источнике (кто может отправлять)
- Ingress на получателе (кто может принимать)

Это позволяет независимо управлять каждым направлением трафика.

### 3. DNS-исключение

Политика `allow-dns` открывает UDP/TCP 53 для всех подов. Без нее поды не смогут резолвить DNS-имена сервисов, и `wget http://back-end-api-app` завершится ошибкой даже при разрешенном HTTP-трафике.

### 4. Изоляция административного контура

Административные сервисы (`admin-*`) полностью изолированы от пользовательских. Это соответствует требованию PropDevelopment по разделению доступа к данным клиентов и собственников.

## Примененные сетевые политики


| Имя политики                  | Тип           | Источник → Назначение |
| ---------------------------------------- | ---------------- | ---------------------------------------- |
| `default-deny-all`                       | Ingress + Egress | Deny all                                 |
| `allow-dns`                              | Egress           | All → DNS:53                            |
| `front-end-to-back-end-api-egress`       | Egress           | front-end → back-end-api:80             |
| `back-end-api-from-front-end-ingress`    | Ingress          | front-end → back-end-api:80             |
| `back-end-api-to-front-end-egress`       | Egress           | back-end-api → front-end:80             |
| `front-end-from-back-end-api-ingress`    | Ingress          | back-end-api → front-end:80             |
| `admin-front-end-to-admin-api-egress`    | Egress           | admin-front-end → admin-back-end-api:80 |
| `admin-api-from-admin-front-end-ingress` | Ingress          | admin-front-end → admin-back-end-api:80 |
| `admin-api-to-admin-front-end-egress`    | Egress           | admin-back-end-api → admin-front-end:80 |
| `admin-front-end-from-admin-api-ingress` | Ingress          | admin-back-end-api → admin-front-end:80 |

## Связь с требованиями безопасности PropDevelopment

Из задания 2 (проверочный лист) и описания компании:

- Контроль данных: сетевая изоляция предотвращает несанкционированный доступ между системами
- Принцип минимальных привилегий: каждый сервис общается только с тем, с кем должен
- Разделение клиентских и административных сервисов: защищает от сценария "один партнер видит данные другого"
- Соответствие ФЗ-152: ограничение потоков персональных данных на сетевом уровне
