# Отчет по результатам анализа Kubernetes Audit Log

## Контекст

Анализ проводился на основе лога audit.log, полученного из кластера Minikube
после запуска simulate-incident.sh. Скрипт имитирует действия злоумышленника,
получившего первоначальный доступ к кластеру через сервисный аккаунт.

Политика аудита фиксировала события уровня RequestResponse для ключевых ресурсов
(pods, secrets, configmaps, serviceaccounts, roles, rolebindings) и уровня Metadata
для всех остальных ресурсов.

## Подозрительные события

1. Доступ к секретам:
   - Кто: system:serviceaccount:secure-ops:monitoring
   - Где: namespace kube-system, ресурс secrets (default-token)
   - Почему подозрительно: сервисный аккаунт из пользовательского namespace
     запросил системные секреты kube-system. Штатная работа мониторинга
     не требует доступа к токенам системных компонентов. Это разведка
     учетных данных для дальнейшей эскалации.

2. Привилегированные поды:
   - Кто: kubernetes-admin
   - Комментарий: под privileged-pod создан с securityContext.privileged: true.
     Привилегированный контейнер получает прямой доступ к устройствам хоста
     и всем пространствам имен ядра - это полный обход контейнерной изоляции.
     Фактически равнозначно root-доступу к узлу.

3. Использование kubectl exec в чужом поде:
   - Кто: kubernetes-admin
   - Что делал: выполнил exec в под CoreDNS (namespace kube-system)
     и прочитал /etc/resolv.conf для получения информации о внутренней
     DNS-инфраструктуре кластера. Типичный шаг разведки перед
     горизонтальным перемещением.

4. Создание RoleBinding с правами cluster-admin:
   - Кто: kubernetes-admin
   - К чему привело: сервисный аккаунт monitoring получил полные права
     cluster-admin через escalate-binding. С этого момента через данный
     аккаунт доступны любые операции в кластере: чтение всех секретов,
     изменение любых ресурсов, управление узлами. Кластер скомпрометирован.

5. Удаление audit-policy.yaml:
   - Кто: kubernetes-admin, попытка от имени admin
   - Возможные последствия: деактивация аудита исключает возможность
     обнаружения последующих действий. Это попытка скрыть следы
     после получения привилегий. Является признаком осведомленности
     атакующего о механизмах защиты кластера.

## Ошибки политики RBAC

- Принцип наименьших привилегий не применен: сервисный аккаунт monitoring
  создан без явного ограничения прав. По умолчанию он наследует права,
  достаточные для выполнения ряда привилегированных действий.

- Кластер разрешает привязку cluster-admin к произвольному субъекту
  без ограничений со стороны Admission Controller. OPA Gatekeeper
  или встроенный ValidatingWebhook отсутствует.

- PodSecurity Admission не настроен для namespace secure-ops:
  привилегированные поды проходят без блокировки.

- Нет ограничения на exec в системные поды (kube-system). Доступ
  к exec должен быть ограничен отдельной ClusterRole с явным
  запретом для namespace kube-system.

- Отсутствует NetworkPolicy, изолирующая системный namespace
  от пользовательских.

- Единственный специалист по ИБ не был уведомлен об изменении
  состава руководителей команд, что нарушило процесс согласования
  архитектурных и конфигурационных решений (зафиксировано в описании
  организационной структуры PropDevelopment).

## Вывод

Зафиксирована классическая цепочка атаки с эскалацией привилегий:

  разведка (чтение секретов)
  - закрепление (привилегированный под)
  - перемещение (exec в системный под)
  - эскалация (cluster-admin через RoleBinding)
  - скрытие следов (удаление audit-policy)

Кластер следует считать полностью скомпрометированным с момента
создания escalate-binding. Рекомендуемые меры первого реагирования:

- немедленно удалить escalate-binding и privileged-pod,
- ротировать все токены сервисных аккаунтов в namespace secure-ops,
- восстановить audit-policy.yaml и убедиться в целостности логов,
- проверить остальные namespace на наличие аналогичных RoleBinding.

Рекомендуемые системные меры:

- настроить PodSecurity Admission (уровень restricted) для всех
  пользовательских namespace,
- ограничить создание RoleBinding c cluster-admin через OPA Gatekeeper,
- внедрить Falco или аналог для real-time обнаружения аномалий
  поверх audit-лога,
- настроить алерты на события categories: exec_into_pod,
  rolebinding_escalation, audit_tampering.
